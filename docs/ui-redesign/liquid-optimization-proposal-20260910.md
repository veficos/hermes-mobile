## 1. 结论与目标边界

当前项目已经具备 Liquid 风格的组件基础，处于“整页收敛与验收”阶段，
不是尚未开始，也不是只剩调几个透明度参数。主要差距是材质角色的光学
区分、全局排版和页面密度的一致性、复杂交互连续性，以及真实设备证据。

“iOS 26.6.0”在本次评估中作为用户指定的视觉方向；没有可核验的该版本
系统截图、SDK 对照或真机样本，不能声称像素级还原，也不臆造版本专属参数。
Flutter Web 当前采用背景模糊、染色、连续圆角与绘制高光，不是原生液态
玻璃或真实光学折射。iOS 构建目前也使用同套 Flutter 材质。

推荐目标：具有 iOS Liquid Glass 层次、排版和交互气质的高质量跨端 UI。
原生玻璃视图或折射 shader 是独立可选研究，不列为 Web 首期的硬性目标。

本轮没有可靠逐张视觉检查条件；以下分为代码确认事实、已有测试证据和
待视觉验证的建议。不提供缺乏测量依据的“还原度百分比”。

## 3. 统一设计方向

### 3.1 四层结构

1. 页面底层：轻微带色的稳定背景，贯穿安全区和过度滚动区域。
2. 内容层：实色消息、列表和编辑区，以文字与留白组织信息。
3. 操作层：顶栏、底栏、输入外壳和操作组使用适度透景玻璃。
4. 模态层：菜单和 Sheet 独立强调，遮罩明确阻断背景操作。

不是所有卡片都玻璃化，也不靠全屏渐变、重阴影或发光边框营造层级。

### 3.2 材质标定

- navigation：优先验证滚动内容经过时的背景连续性，降低厚重面板感。
- control：优先突出轮廓和可点击性；输入内容区域仍保持稳定对比度。
- overlay：优先区分前后层级；可比导航更实，避免背景内容穿透干扰阅读。
- 同一物理表面只拥有一套模糊、染色、高光；子按钮通过状态色表达交互。
- 浅色评估白底上的轮廓；深色评估边缘亮度和灰雾感，避免简单反色。
- 在安静及复杂背景上分别比较三组候选，选定后写回 recipe；不直接把
  任意新 alpha/blur 数字当成“更接近 iOS”的证据。
- 四套配色只改变色彩关系，不产生四套互不兼容的布局或玻璃规则。

### 3.3 排版与对齐建议值

以下是待首轮整页样张确认的产品建议，不是 Apple 官方版本参数：

- 手机正文 16–17，列表标题 16–17，辅助文字 13–14；紧凑桌面密度另设档位。
- 中文聊天行高从 1.5–1.65 范围比较；代码字号独立，允许横向滚动。
- 页面边距以 16 为主，宽手机可 20；4/8/12/16/24/32 形成间距序列。
- 列表头像使用统一框，建议 44–48；短文垂直居中，多行内容顶部对齐。
- 视觉图标统一线宽/尺寸；点击区至少 44×44，不把图形本身放大到 44。
- 状态标签、尾部菜单不得挤占标题；长名称与 2x 文本允许自然增高。
- 验证 Apple 平台实际字体解析，采用可合法使用的系统字体回退；不将
  SF 字体文件直接打包到 Web 来模仿原生。
- 保留现有 token 为基线，新增语义化手机/宽屏档位，不散落页面硬编码。

## 4. 页面级优化清单

### 聊天

- 统一正文、工具摘要、审批内容的阅读起始线；用户/助手角色仍可用位置
  和底色区分，不强制所有气泡等宽。宽屏限制阅读宽度并独立安排侧栏。
- 输入框、附件、引用和操作按钮形成一个明确整体；外壳共享材质。
- 审批显示待处理、提交中、已通过/拒绝、失败/过期状态；操作成功后保留
  可追溯结果。避免重复提交；服务端决定权限，UI 不自动扩大授权范围。
- 审批主次按钮明确，长标签换行；键盘和屏幕阅读器可定位到结果。
- 历史顶部始终区分加载中、失败重试和已到开头；读历史时新消息仅提示，
  不抢夺位置，只有用户明确返回最新才恢复追随。
- 分离等待首个 token 与已收到内容：前者有等待状态，后者及时显示已收到
  文本，不以人工逐字动画掩盖整段响应或拖慢输出。
- 用同一真实业务场景串联十页历史、迟到图片、工具展开、窗口裁剪、
  键盘、流式消息、切换会话及失败重试；逐帧验证阅读位置。

### 机器人

- 保留已合并的紧凑概览；首屏重点是“选机器人并开始使用”。
- 已有创建/管理操作保持清晰分工；避免重新增加第二套中心卡片。
- 列表统一头像框、名称/描述列、状态和尾部操作；检查真实图裁剪、
  加载与失败回退，不只验收占位图。
- 列表仅展示影响选择的状态，服务、模型、运行时细节进入现有诊断展开区。
- 活跃/选中与在线/运行不能只依赖颜色；筛选与排序基于真实数量决定，
  不为了视觉丰富而增加重复控件。

### 任务

- 搜索、筛选、视图切换和新建形成稳定工具区；窄屏允许有序换行。
- 标题为第一层，状态/优先级为第二层，负责人/评论为第三层。
- 手机优先推荐列表；保留用户已有视图偏好，看板显式提示横向还有列。
- 看板列内纵向滚动、整体横向滚动和下拉刷新必须有清晰手势边界。
- 批量操作区与底部导航/安全区不重叠；选择、移动中、失败重试有连续反馈。
- 筛选后空结果与项目本来无任务分开表达，提供对应的清除/新建入口。

### 更多、设置与次级页面

- 分组目录控制图标底色数量、行高、分隔线起始位置；连接状态只展示一次。
- 搜索可扩展中文/英文常见别名，但使用明确映射避免误匹配。
- 外观页预览真实的导航+内容+输入/弹层，而非只预览一张玻璃卡片。
- 设置、配置编辑、文件、Git、通知和终端统一返回/保存/取消与未保存提示；
  编辑和终端内容仍为实色，不追求整屏透明。
- 危险操作与普通设置分组，保留确认机制；Sheet 关闭后焦点回到来源控件。

## 6. 总验收矩阵

- 视口：320、390、430、768、1280；宽屏必须含真实导航和填充内容。
- 明暗与四配色：核心状态全覆盖；组合测试按风险选取并记录例外。
- 辅助功能：1x/2x 字体、减少透明度/动画、高对比、Tab/Enter/Escape、
  焦点返回、VoiceOver 阅读顺序；普通正文对比度至少 4.5:1。
- 玻璃对比度评估实际复合背景，不能只测前景与 token 原色。
- 滚动验收：以同一消息 ID 的屏幕位置为准，区分用户主动移动与系统漂移；
  无手势时受控布局变化目标偏移不超过 2 逻辑像素，无中间帧消失/跳底。
- 端到端场景使用真实服务的隔离测试数据，避免对生产审批/任务执行写入。
- 性能：Release 模式记录设备/OS/浏览器/渲染器、数据量、UI/raster p50/p95、
  超预算比例；60Hz 按 16.7ms 预算评估，120Hz 另设 8.3ms 目标。
  明确引擎慢帧统计不等于合成器实际丢帧，不能把无样本记作零耗时。
- 性能不足时先减少玻璃采样区域、独立表面和重绘，保持阅读稳定；
  不通过删减内容、延迟文字或隐藏失败状态使指标好看。
- 最终构建保留 Classic 默认值、用户 Liquid/配色/辅助偏好；必要时可退回
  Classic。9000 端口响应与构建哈希一致只证明部署正确，不证明 UI 已验收。

## 7. 推荐立即开始的最小闭环

先完成“390px 明暗聊天 + 机器人列表 + 一个打开的 Sheet”的整页对照，
同时解释现有两项 golden 差异。通过这一小组场景确认材质、字号、边距与
标题规则后，再迁移任务和更多页面。聊天复杂状态验证可独立推进。
不要以继续增加零散测试或反复构建代替视觉设计决策。
